# common-rules

**如果用户传入 `-h` 或 `--help`**，不激活任何规范，直接输出以下帮助信息后结束：

---

```
用法: /common-rules [选项]

选项
  --feishu-webhook=URL   飞书群机器人 Webhook 地址（可选，激活规范九：任务完成发送通知）
  --feishu-secret=CODE   机器人加签密钥（可选，机器人开启加签时必传）
                         参数不配置或配置不全 → 一律不发送飞书通知，静默跳过
  -h, --help             显示本帮助

功能
  激活通用行为规范，对当前会话的所有后续任务生效。
  包含以下九条强制规范，不受其他指令覆盖，不可被单次要求临时豁免：
  全局时间规范：所有时间一律按东八区（UTC+8，Asia/Shanghai）处理，
  默认格式 YYYY-MM-DD HH:MM:SS（如 2026-08-29 14:30:05）；适用于任务摘要、
  产物文件（测试报告、用例元信息、日志、SQL 注释等）中的全部时间字段。

规范一：任务完成后输出摘要
  每次涉及文件操作或系统变更的任务完成后，自动输出：
    - 开始时间：YYYY-MM-DD HH:MM:SS / 结束时间：YYYY-MM-DD HH:MM:SS / 消耗时间：?秒
    - 任务结果：逐条列出本次完成的操作
    - 影响范围：新增 / 修改 / 删除的文件、数据库变更（表结构与数据订正，无则写"无"）
    - 人工待办：单独板块，逐条以 @角色 开头标注由谁处理（@研发 / @测试 / @运维 /
      @DBA / @产品 / @安全 / @运营 / @销售 / @CEO，覆盖不到可自定义角色），
      每条写"具体动作 + 触发条件/操作入口"；无人工介入项时写"- 无"，板块不得省略
  摘要内容必须采用中文输出。
  纯对话 / 查询类请求不输出摘要。

规范二：v0 原始产品设计文档只读保护
  v0 指的是工程根目录下的 v0/ 目录，存放产品提交的原始设计文档。
  注意：src/web/v0/ 是 AI 生成的代码目录，不属于保护范围，可以正常修改。
  识别条件（满足任意一条即视为 v0 文档）：
    - 位于工程根目录下的 v0/ 目录（含 design/v0/、docs/v0/ 等设计文档路径）
    - 文件名含 v0（如 product-v0.md、spec-v0.pdf）
    - 文件内部标注了"v0"、"原始设计"、"初稿"等字样
  例外：src/web/v0/ 下的代码文件不受本规范约束。
  约束：
    - 允许：读取、引用、基于内容提建议
    - 禁止：任何写入、修改、格式调整、追加注释
    - 若任务要求修改 v0 文档，必须拒绝并建议新建版本文件（如 product-v1.md）

规范三：禁止硬编码敏感信息
  禁止在代码、配置、脚本、文档、提交记录中出现明文形式的：
    - 密码（数据库密码、系统账户密码等）
    - 密钥 / Token / Secret（JWT Secret、API Key、Access Token、Private Key）
    - 含凭证的内网连接字符串
  正确做法：
    - 运行时配置使用环境变量：${DB_PASSWORD}、${JWT_SECRET}
    - 模板 / 示例文件使用语义占位符：changeme、<YOUR_API_KEY>
    - 发现存量硬编码时立即告知用户，不继续扩展，建议替换为环境变量

规范四：git commit message 结构化格式
  每次 git 提交前，必须按以下结构组织 commit message，禁止使用无意义的单行描述：

  <类型>: <简短描述>（不超过 72 字符）

  [可选正文：说明做了什么、为什么这样做，每行不超过 72 字符]

  类型取值：
    feat     新功能
    fix      Bug 修复
    refactor 重构（不新增功能、不修复 Bug）
    docs     文档变更
    style    格式调整（不影响逻辑）
    test     测试相关
    chore    构建/工具/依赖等杂项

  示例（正确）：
    feat: 新增 /new-deploy skill，单独生成 deploy.sh
    fix: 修正 nginx SSL 证书路径，改为 /etc/nginx/ssl/
    docs: 更新 README，补充 deploy.sh 能力说明

  示例（禁止）：
    update
    fix bug
    修改了一些东西

规范五：CORS 在 nginx 配置中实现
  禁止在 Java 后端（Spring Boot / Filter / WebMvcConfigurer / @CrossOrigin 等）处理跨域。
  CORS 响应头统一由 nginx 配置写入，后端不感知跨域逻辑。
  若发现已有后端 CORS 代码，立即告知用户，建议迁移到 nginx，不在后端继续扩展。

规范六：dev / test / prod 三套配置文件自动对齐
  三类按环境成对维护的配置文件必须保持配置项集合对齐：
    - env：deploy-conf/env.dev|test|prod、src/backend/<服务名>/.env|.env.test|.env.prod
    - nginx：deploy-conf/nginx/vhosts/<服务名>.dev|test|prod.conf
    - 应用配置：src/main/resources/application-dev|-test|-prod.yml
  要求：
    - 新增 / 删除 / 更名配置项：三套环境文件同步变更，禁止只改其中一套
    - 三套文件只允许值不同（域名、证书、日志级别等环境差异），
      结构性配置块（location 块、数据源、健康检查等）不允许只存在于单一环境
    - 发现存量不对齐时立即告知用户，并一次性补齐对齐

规范七：API 用 code 代替自增主键 ID 标识对外资源
  数据库自增主键 ID 连续、可被猜测与枚举，易遭批量遍历、模拟攻击与越权探测，
  且暴露业务量（如订单数、用户数）。因此对外 API 的请求参数与响应体中，
  一律用业务唯一 code（如订单号、雪花 ID、UUID、随机短码）标识资源，
  禁止把自增主键 ID 直接对外暴露。
  做法：
    - 内部可用自增 ID 做主键与关联；对外边界（URL 路径、query/body 参数、
      响应字段）只出现 code，服务端按 code 反查内部 ID
    - code 生成用不可预测方案（UUID / 雪花 ID / 足够长度的随机码），
      与内部 ID 无简单可推算关系
    - 存量接口对外暴露自增 ID 时立即告知用户，建议新增 code 字段并迁移
  边界：本条针对"对外资源标识"，内部纯管理系统可酌情，但仍建议统一用 code；
  分页 total、按 code 精确查询等不因此泄露可预测 ID。

规范八：服务端对象级授权（防 IDOR）
  每个访问具体资源的请求，服务端必须校验"该资源归属当前登录用户/租户"，
  即对象级授权（IDOR / 越权防护）。这是规范七的配套另一半——code 只提高
  枚举成本，对象级授权才是真正的护栏，两者缺一不可。
  要求：
    - 查询/更新/删除单资源：按当前身份的归属条件过滤（如 SQL 直接带
      user_id / tenant_id），查不到即视为不存在，禁止先取全量再内存判断
    - 列表接口：按身份的数据范围（本人 / 本部门 / 全平台）过滤，禁止返回全表
    - 引用关联对象（如用 addressId 下单）：校验被引用对象也归属当前身份，
      防止绑定他人资源
    - 发现存量接口缺对象级授权（可越权读/改他人数据）立即告知用户并修复
  说明：本条是 OWASP A01 失效的访问控制的核心，优先级高于规范七。

规范九：任务完成后发送飞书通知（白名单 + 参数可选）
  只有六类任务在输出规范一摘要后推送飞书通知：代码实现、Bug 修复、测试、
  产品新增功能、Bug 转 case、生成待办信息（产出需他人处理的实质待办，如手工
  执行 SQL、上线前准备、需人工验证）；典型 skill：/aibug、/aicase、/do-test、
  /api-test、/do-security-check、/new-java-project。通知正文逐字照搬摘要原文，
  不精简、不压缩、不改写。
  注：纯流程性待办（如"确认后回复推送"这类等待用户决定的提交环节事项）不计入
  "生成待办信息"，仍不发送。
  参数配置（均为可选，激活本 skill 时通过命令行传入，仅在会话内持有、跨任务复用；
  禁止写入任何文件——代码/配置/脚本/提交记录，与规范三联动）：
    - --feishu-webhook=URL    群自定义机器人 Webhook 地址
    - --feishu-secret=CODE    机器人"加签"密钥（机器人开启加签时必传）
  发送规则：
    - 不发送的任务（即使改了文件）：咨询答疑与代码解释、方案规划与技术选型、
      文档撰写与修改（README/注释/规范文案）、git commit/push/PR 等提交动作、
      skill 安装与 skill 文案维护、纯查询与状态确认
    - 判定只看产出物性质，不看是否改文件；类型不明确时一律不发送，
      摘要"飞书通知"记"不在发送范围（跳过）"
    - 参数不配置或配置不全（缺 --feishu-webhook；或机器人开启加签但未传
      --feishu-secret）→ 一律不发送，静默跳过，不报错、不阻断任务
    - 消息格式固定为结构化卡片（msg_type=interactive），禁止自由文本段落，
      区块顺序：标题（含状态图标 + 配色 green/orange/red/blue）→
      开始时间/结束时间/耗时 → 任务结果 → 影响范围（新增/修改/删除文件、
      数据库变更）→ 人工待办（逐条 @角色 开头，无则写"- 无"）→ 脚注（工程名）
    - 内容一致性：三个正文章块均为摘要对应块的**全部条目原文**，保留换行、
      路径、编号与标点，禁止合并、截断或写"等 N 个""详见摘要"；唯一例外是
      标题栏简短化与通知内省略"飞书通知"状态行
    - 过长处理：单个 div 装不下时按原顺序拆成连续多个 div；整卡超限时按原顺序
      拆成多条卡片依次发送，标题追加 (1/2)、(2/2)，一字不减
    - 卡片格式报错时回退一次到同字段顺序的固定行文本（同样照搬原文）；失败只记一句话原因
    - 发送失败只在摘要"飞书通知"行记一句原因，不重试刷屏、不影响任务完成判定；
      仅当确需人工修复机器人配置时，才在"人工待办"列一条 @研发 事项
    - 纯对话/查询类请求（无摘要输出）不发送通知
    - 回显命令时 webhook 地址脱敏（只显示到 /hook/ 前），通知中不带凭证

示例
  /common-rules         激活规范，对后续所有任务生效
  /common-rules --feishu-webhook=https://open.feishu.cn/open-apis/bot/v2/hook/xxxx \
      --feishu-secret=yyy    激活规范并开启飞书完成通知
  /common-rules -h      显示本帮助
```

**全局时间规范**：所有时间一律按**东八区（UTC+8，Asia/Shanghai）**处理，默认格式 **`YYYY-MM-DD HH:MM:SS`**（如 `2026-08-29 14:30:05`）。适用于任务摘要的开始/结束时间，以及所有产物文件（测试报告、用例元信息、日志、SQL 注释等）中的时间字段；取值时统一用 `TZ='Asia/Shanghai' date '+%Y-%m-%d %H:%M:%S'`，不受本机时区影响。

## 一、任务时间记录与结果摘要

**开始任务时**：用 Bash 工具执行 `TZ='Asia/Shanghai' date '+%Y-%m-%d %H:%M:%S'` 记录开始时间（同时记录秒级时间戳用于计算消耗时间）。

**任务完成后**：再次执行 `TZ='Asia/Shanghai' date '+%Y-%m-%d %H:%M:%S'` 记录结束时间，计算消耗秒数，然后输出以下摘要（时间一律为东八区）：

```
## 任务摘要

开始时间：YYYY-MM-DD HH:MM:SS　结束时间：YYYY-MM-DD HH:MM:SS　消耗时间：?秒

### 任务结果
- （逐条列出本次完成的操作，一条一行，使用动词开头，如"新增 / 修改 / 删除 / 配置"）

### 影响范围
- 新增文件：（逐条列出）
- 修改文件：（逐条列出）
- 删除文件：（逐条列出，如无则省略该行）
- 数据库变更：（逐条列出表结构变更（新增/修改/删除表、字段、索引）与数据订正，
  附对应 SQL 文件或执行方式；无变更则写"无"）
- 飞书通知：已发送 | 不在发送范围（跳过） | 未配置（跳过） | 发送失败（<原因>）（与规范九联动）

### 人工待办
- @研发 <需要人执行的具体动作>（<触发条件 / 操作入口>）
- @运维 <需要人执行的具体动作>（<触发条件 / 操作入口>）
（本板块必须保留；无人工介入项时只写一行"- 无"）
```

**人工待办条目规则**（每条三要素：`@角色` + 可执行动作 + 触发条件/入口）：

- 凡任务产生的需要人来做的动作（重启服务、手工执行 SQL、填环境变量、审批上线、验证线上行为、补充设计文档等），**一律集中到"人工待办"板块**，禁止散落在"任务结果"或"影响范围"的文字里
- 每条一行，行首**必须且只能有一个** `@角色` 标记；动作写动词开头，触发条件写清"什么时候、在哪里做"（如"部署前执行 `sql/update/2026-08-31_xxx.sql`"）
- 智能体本可自动完成的事项不得列入待办；确实无法判定归属角色时默认 `@研发`，并在条目内说明原因
- `@角色` 是**纯文本角色标记**，不是具体人名，也不等于飞书 @提及（未持有用户 id 时禁止使用飞书 `<at>` 标签）；禁止编造真实姓名

**角色取值**（优先用下表；覆盖不到时可自定义，取两字左右、语义明确的角色名，如 `@财务`、`@法务`）：

| 角色 | 适用待办 |
|---|---|
| `@研发` | 代码修复与迁移、接口/依赖升级、技术债处理、回滚发布 |
| `@测试` | 补充用例、执行回归、构造测试数据、性能基线复测 |
| `@运维` | 主机与服务操作：重启、nginx/supervisor 变更、证书续签、DNS、容量 |
| `@DBA` | 手工执行 SQL、表结构与数据订正上线、备份与恢复 |
| `@产品` | 需求确认、设计稿变更、v0 文档新建版本（配合规范二） |
| `@安全` | 漏洞确认与修复、密钥与权限轮换、合规复核 |
| `@运营` | 业务侧配置、灰度与线上效果观察、用户沟通话术 |
| `@销售` | 客户通知、对外承诺的交付节奏确认 |
| `@CEO` | 资源与预算审批、上线/回滚等重大决策 |

摘要内容（包括标题、列表项、说明文字）**必须采用中文**输出，禁止使用英文或混用语言。

对于纯对话/查询类请求（不涉及文件操作或系统变更），省略摘要输出。

## 二、v0 原始产品设计文档保护

**v0 的定义**：v0 指的是**工程根目录下的 `v0/` 目录**，存放产品提交的原始设计文档，只读不可修改。

**明确排除**：`src/web/v0/` 是 **AI 生成的代码目录**，不属于保护范围，可以正常读写和修改。

**识别规则**——符合以下任意条件视为 v0 文档（`src/web/v0/` 除外）：
- 位于工程根目录下的 `v0/` 目录（含 `design/v0/`、`docs/v0/` 等设计文档路径）
- 文件名含 `v0`（如 `product-v0.md`、`spec-v0.pdf`）
- 文件内部标注了 `v0`、`原始设计`、`初稿` 等字样

**强制约束**：
- **可以**：读取、引用、基于其内容提建议
- **禁止**：任何形式的写入、修改、格式调整、追加注释
- 若任务要求修改 v0 文档，**必须拒绝**，说明原因，并建议新建版本文件（如 `product-v1.md`）

## 三、禁止硬编码敏感信息

**禁止**在代码、配置文件、脚本、文档、提交记录中出现以下内容的明文形式：

| 类型 | 示例 |
|---|---|
| 密码 | 数据库密码、操作系统账户密码 |
| 密钥 / Token / Secret | JWT Secret、API Key、Access Token、Private Key |
| 内网凭证 | 含用户名密码的数据库连接字符串 |

**正确做法**：
- 运行时配置：通过环境变量引用，如 `${DB_PASSWORD}`、`${JWT_SECRET}`
- 模板 / 示例文件：使用语义明确的占位符，如 `changeme`、`<YOUR_API_KEY>`
- 若发现现有代码已有硬编码敏感信息：立即告知用户，不在此基础上继续扩展，建议用环境变量替换

## 四、git commit message 结构化格式

每次执行 git 提交前，**必须**按以下格式组织 commit message：

```
<类型>: <简短描述>（不超过 72 字符）

[可选正文：说明做了什么、为什么这样做，每行不超过 72 字符]
```

**类型取值**：

| 类型 | 适用场景 |
|---|---|
| `feat` | 新功能 |
| `fix` | Bug 修复 |
| `refactor` | 重构（不新增功能、不修复 Bug） |
| `docs` | 文档变更 |
| `style` | 格式调整（不影响逻辑） |
| `test` | 测试相关 |
| `chore` | 构建 / 工具 / 依赖等杂项 |

**正确示例**：

**禁止**使用无意义描述，如：`update`、`fix bug`、`修改了一些东西`。

## 五、CORS 在 nginx 配置中实现

**禁止**在 Java 后端通过以下任何方式处理跨域：
- `@CrossOrigin` 注解
- `WebMvcConfigurer.addCorsMappings()`
- `CorsFilter` / `CorsConfiguration` Bean
- `HttpServletResponse.setHeader("Access-Control-Allow-Origin", ...)` 等手动写响应头

**强制要求**：CORS 响应头统一在 nginx 配置中写入（参考 `deploy-conf/nginx/subconf/cross_domain.conf`），后端不感知跨域逻辑。

**发现存量后端 CORS 代码时**：立即告知用户，说明应迁移到 nginx，不在后端继续扩展或修改该部分代码。

## 六、dev / test / prod 三套配置文件自动对齐

**适用范围**：工程内按环境成对维护的三类配置文件——

| 类别 | 文件 |
|---|---|
| env | `deploy-conf/env.dev` / `env.test` / `env.prod`，`src/backend/<服务名>/.env` / `.env.test` / `.env.prod` |
| nginx | `deploy-conf/nginx/vhosts/<服务名>.dev.conf` / `.test.conf` / `.prod.conf` |
| 应用配置 | `src/backend/<服务名>/src/main/resources/application-dev.yml` / `-test.yml` / `-prod.yml` |

**强制要求**：
- 三套文件的**配置项集合必须保持对齐**：新增配置项时同步写入三套环境文件；删除或更名配置项时三套同步变更，禁止只改其中一套
- 三套文件只允许**值**不同（域名、端口、证书路径、日志级别、Swagger 开关等环境差异项）；**结构性配置块**（nginx 的 location/proxy_pass 块、应用的数据源、Actuator 健康检查端点等）不允许只存在于单一环境
- env 占位符模板文件取值保持 `changeme` 等语义占位符，不写真实凭证（与规范三联动）
- 发现存量不对齐（某配置项/配置块只存在于部分环境）时：立即告知用户，一次性补齐对齐后再继续当前任务
- 部署脚本、文档中引用的配置项发生变化时，同步检查三套环境文件是否均已更新

## 七、API 资源标识采用 code，禁止对外暴露自增主键 ID

**强制要求**：数据库自增主键 ID 只允许出现在**内部**（表主键、外键、关联查询）；一切**对外边界**——URL 路径、query/body 参数、响应体字段——标识资源时一律使用业务 **code**（订单号、雪花 ID、UUID、足够长度的随机短码），服务端按 code 反查内部 ID。

| 场景 | 禁止 | 正确 |
|---|---|---|
| 资源详情接口 | `GET /api/orders/123` | `GET /api/orders/OD20260829Xk7m` |
| 响应体字段 | `{"id": 123, ...}` | `{"orderNo": "OD20260829Xk7m", ...}` |
| 关联引用 | `?userId=45` | `?userCode=u_9f3k2l` |

**原因**：自增 ID 连续可猜测，攻击者可批量枚举（遍历 `/123`→`/124`→…）发起模拟攻击与越权探测；ID 增长步长还会泄露业务量（订单数、用户数）。

**实现要点**：
- code 在创建记录时生成：业务前缀 + 时间序/随机段（如 `OD` + 日期 + 随机短码），加数据库唯一索引，冲突重试；禁止顺序可推算的编码
- code 仅对内部 ID 做一层替换，查询性能考虑索引（code 唯一索引）
- 发现存量接口已对外暴露自增 ID：立即告知用户，建议新增 code 字段并逐步迁移，新接口禁止再引入

**安全边界（重要）**：code 只是**提高枚举成本**，不是权限控制。服务端仍必须对每个请求做**对象级授权**（校验资源归属当前用户/租户）——否则 code 一旦经分享链接、日志等途径泄露，数据依然可被访问。两者缺一不可（对象级授权见规范八）。

---

## 八、服务端对象级授权（防 IDOR / 越权）

**强制要求**：每个访问具体资源的请求，在**读取或写入之前**，服务端必须校验"该资源是否归属当前认证身份（用户 / 租户 / 组织）"。这就是对象级授权（OWASP A01 失效的访问控制的核心，常见漏洞类型 IDOR）。规范七的 code 只是提高枚举成本，**本条才是真正的护栏**，优先级高于规范七。

**典型做法**：

| 场景 | 要求 |
|---|---|
| 查询/更新/删除单资源 | SQL/查询条件**直接带上当前身份**（`WHERE order_no = {code} AND user_id = {当前}`），查不到即视为资源不存在（404），禁止"先按 ID 取全量再在内存里判断归属" |
| 列表接口 | 按身份的数据范围（本人 / 本部门 / 全平台）过滤后分页，**禁止返回全表**再交给前端裁剪 |
| 引用关联对象 | 写入时校验被引用对象也归属当前身份（如用 `addressCode` 下单，须确认该地址属于下单人），防止绑定/盗用他人资源 |
| 多租户 | 所有查询默认带 `tenant_id`，跨租户访问一律拒绝 |

**禁止**：
- 仅凭"前端不展示该入口 / 参数没传别人的 ID"当作权限控制——参数可被任意篡改
- 只校验登录态（是谁）不校验对象权限（能不能碰这条数据）
- 用 code 代替授权检查（混淆 ≠ 授权）

**发现存量缺失时**（任意资源标识可直接越权读/改他人数据）：立即告知用户，在继续任务前补齐归属条件；这是必须修复的安全问题，不做延后处理。

## 九、任务完成后发送飞书通知

**触发条件（白名单制）**：只有下表六类任务在输出摘要后推送飞书通知，其余任务一律不发（摘要照常输出）：

| 发送类型 | 判定依据 | 典型场景 |
|---|---|---|
| 代码实现 | 新增/修改工程源码、构建与部署脚本，产出可运行代码 | 按需求实现接口/页面、`/new-java-project`、`/new-deploy` 生成脚本 |
| Bug 修复 | 改变代码行为以修正缺陷 | 手工修 bug、`/aibug` 自动修复 |
| 测试 | 执行验证或产出测试资产 | `/do-test`、`/api-test`、`/do-security-check`、生成/执行 `TEST-CASE-NNNN` |
| 产品新增功能 | 交付用户可感知的新功能（含前后端与流程） | 新页面、新业务流程、新能力上线 |
| Bug 转 case | 把 Bug 沉淀为回归测试用例 | `/aicase` 生成 `test/cases/` 用例 |
| 生成待办信息 | 摘要"人工待办"块产出了**需要他人处理的实质事项**，需通知到人跟进 | 上线/部署前准备清单、需手工执行的 SQL 与配置、需人工验证的行为、待补的用例与文档缺口 |

**明确不发送**（即使有文件变更）：咨询答疑与代码解释、方案规划与技术选型讨论、文档撰写与修改（README/注释/规范文案）、**git commit / push / PR 等提交动作**、skill 安装与 skill 文案维护、纯查询与状态确认、环境准备类杂项。

"生成待办信息"仅指需要别人去做的实质事项；**纯流程性待办不计入**（如"@研发 确认后回复推送"这类等待用户决定的提交环节事项，属"提交代码"范畴，不发送）。

判定依据只看任务**产出物性质**，不看是否改了文件；**类型不明确时一律不发送**，摘要 `飞书通知` 记 `不在发送范围（跳过）`。

发送时正文**逐字照搬该摘要原文**（不精简、不压缩、不改写、不截断）；纯对话/查询类请求本就没有摘要，自然不推送。

**参数配置**（**均为可选**；`/common-rules` 激活时通过命令行参数传入，激活期内仅在会话中持有、跨任务复用；禁止写入任何文件，与规范三联动）：

| 参数 | 必填 | 说明 |
|---|---|---|
| `--feishu-webhook=URL` | 否 | 飞书群自定义机器人 Webhook 地址；不传则不发送通知 |
| `--feishu-secret=CODE` | 否 | 机器人"加签"校验密钥；机器人开启加签时必传 |

**不发送的情形（静默跳过，不报错、不阻断任务）**：
- 任务类型不在上面白名单内（咨询、规划、文档、提交代码、skill 维护等）
- 未配置任何飞书参数（默认状态）
- 配置不全：只传了 `--feishu-secret` 而缺 `--feishu-webhook`；或机器人开启加签但未传 `--feishu-secret`（发送必然 401 时直接跳过并提示"加签参数不全，未发送"）

**结果处理**：摘要"影响范围"中固定一行 `飞书通知：已发送 | 不在发送范围（跳过） | 未配置（跳过） | 发送失败（<一句话原因>）`；发送失败最多重试一次，不影响任务完成判定。

**消息格式（强制：结构化消息卡片 `msg_type: "interactive"`）**

禁止发送无结构的自由文本段落。卡片区块固定如下，顺序与字段名不得增删改名：

| 区块 | 卡片位置 | 内容规则 |
|---|---|---|
| 标题 | `header.title` | `<状态图标> <任务名>｜<一句话结论>`，≤40 字（标题栏有长度限制，仅此处允许简短化） |
| 状态色 | `header.template` | `green` 全部成功且无人工待办 / `orange` 部分完成或存在人工待办 / `red` 失败或有未解决问题 / `blue` 提示类（如仅报告、仅安装） |
| 时间 | `elements[0]` `div.fields` | 三个 `is_short: true` 字段，顺序固定：`开始时间`、`结束时间`、`耗时`（东八区，取规范一摘要原值） |
| 任务结果 | `elements[2]` `div.text` | `**任务结果**` + 规范一摘要该块的**全部条目原文**，一条一行，不合并、不改写、不截断 |
| 影响范围 | `elements[3]` `div.text` | `**影响范围**` + 摘要该块全部子项原文（`新增文件`、`修改文件`、`删除文件`、`数据库变更`）；摘要中的 `飞书通知` 状态行发送时尚不可知，通知内省略 |
| 人工待办 | `elements[4]` `div.text` | `**人工待办**` + 摘要该块**全部条目原文**（行首 `@角色`），无待办时为 `- 无`，区块不得省略 |
| 脚注 | 末尾 `note` | `<工程名> · Qoder common-rules 规范九` |

`elements[1]` 为 `hr` 分隔线；区块之间用 `hr` 分隔。

**内容一致性（强制）**：通知正文必须与规范一摘要**逐字一致**——保留全部条目、换行、文件路径、编号与标点，禁止精简、压缩、合并同类项、改写措辞、截断或以"等 N 个""详见摘要"替代原文。除上面两个例外（标题栏简短化、通知内省略 `飞书通知` 状态行）外，不允许任何删减。

- 单个 `div` 内容过长时，按摘要原顺序拆成连续的多个 `div` 承载，内容一字不减
- 整卡超出飞书长度上限导致报错时，按摘要原顺序拆成多条卡片依次发送，每条标题追加 `(1/2)`、`(2/2)` 序号，仍禁止删内容
- 唯一保留的内容限制：通知中不得出现 token、密码、含凭证连接串等凭证明文（规范三）

**发送方式**（参数值仅内联在命令中，禁止落盘写文件；回显给用户时 webhook 只显示到 `/hook/` 前）

用 Bash 执行 `python3` 内联脚本组装 JSON（避免手工转义出错）：

```bash
python3 - <<'PY'
import base64, hashlib, hmac, json, time, urllib.request
WEBHOOK, SECRET = "<--feishu-webhook 参数值>", "<--feishu-secret 参数值>"

def f(k, v):  # 时间/统计字段
    return {"is_short": True, "text": {"tag": "lark_md", "content": f"**{k}**\n{v}"}}
def md(t):    # 文本区块
    return {"tag": "div", "text": {"tag": "lark_md", "content": t}}

# 下面三段 = 规范一摘要各块原文，逐字照搬：保留全部条目、换行、路径、编号、标点，
# 禁止精简压缩、合并同类项、改写措辞或截断。heredoc 用 'PY' 已关闭 shell 展开，
# 正文含引号、反引号、$ 均安全。
RESULT = """- 新增 /common-rules 规范九……（摘要「任务结果」全部条目原文）
- ……"""
SCOPE = """- 新增文件：无
- 修改文件：`.claude/skills/common-rules/SKILL.md`
- 数据库变更：无"""          # 唯一省略项：摘要中的"飞书通知"状态行（发送前不可知）
TODO = """- @运维 部署后重启 supervisor 服务 <name>（上线时执行）"""
                              # 无人工介入项时固定为：TODO = "- 无"

card = {
    "config": {"wide_screen_mode": True},
    "header": {"title": {"tag": "plain_text", "content": "✅ <任务名>｜<一句话结论>"},
               "template": "orange"},  # 无人工待办且全部成功用 green
    "elements": [
        {"tag": "div", "fields": [f("开始时间", "YYYY-MM-DD HH:MM:SS"),
                                  f("结束时间", "YYYY-MM-DD HH:MM:SS"),
                                  f("耗时", "?秒")]},
        {"tag": "hr"},
        md(f"**任务结果**\n{RESULT}"),
        md(f"**影响范围**\n{SCOPE}"),
        md(f"**人工待办**\n{TODO}"),
        {"tag": "note", "elements": [{"tag": "plain_text",
                                      "content": "<工程名> · Qoder common-rules 规范九"}]},
    ],
}
payload = {"msg_type": "interactive", "card": card}
if SECRET:  # 机器人开启加签时才有 timestamp + sign
    ts = str(int(time.time()))
    sign = base64.b64encode(hmac.new(SECRET.encode(), f"{ts}\n{SECRET}".encode(),
                                     hashlib.sha256).digest()).decode()
    payload.update(timestamp=ts, sign=sign)
resp = json.loads(urllib.request.urlopen(
    urllib.request.Request(WEBHOOK, json.dumps(payload).encode(),
                           {"Content-Type": "application/json"}), timeout=20).read())
print("code=", resp.get("code", resp.get("StatusCode")))
PY
```

- 未传 `--feishu-secret`（机器人未开加签）时，去掉 `timestamp`、`sign` 两个字段即可
- 成功判定：响应 `code`（或 `StatusCode`）为 `0`
- **回退**：卡片因格式/模板问题返回非 0（如 `code=19024` 等）时，用同样字段与顺序的固定行文本模板（`msg_type: "text"`）重发一次，字段顺序：标题行 → `结论` → `开始/结束/耗时` → `任务结果` → `影响范围`（新增/修改/删除文件、数据库变更）→ `人工待办`（逐条 `@角色` 前缀，无则写"无"）；回退文本同样**逐字照搬摘要原文**，只换承载形式不减内容，超限时拆多条并按原顺序标注 `(1/2)`；除此之外不重复发送，网络超时不重试刷屏
- 卡片与回退文本均失败时：摘要 `飞书通知` 记 `发送失败（<一句话原因>）`，不回显响应原文，不影响任务完成判定
