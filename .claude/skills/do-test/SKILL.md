# do-test

驱动工程中所有测试场景的执行：API 基本功能验证（委托 /api-test）+ 场景用例验证（test/cases/），汇总为统一测试报告。

**定位**：测试编排入口。本身不做具体探测逻辑，API 部分完全委托 /api-test，场景部分按用例定义执行。

**触发条件**：用户要求运行全部测试、执行测试场景、回归验证，或直接输入 /do-test。

> **执行方式：必须串行执行，禁止并行。** 同一时刻只允许一个本 skill 实例；**每个用例通过子 agent 执行，严格逐条串行**——上一个用例的子 agent 出结论后，才可为下一个用例启动子 agent。禁止并行启动多个实例、并行启动多个子 agent 同时执行不同用例，也禁止与 /aibug、/aicase 并发运行。

## 一、前置检查

0. **确定任务范围**：解析 `--task`（可多个：`api` / `cases`）；传入 `--case` 时隐含包含 `cases`；未传 `--task` 与 `--case` 时默认 `api + cases` 全部执行。取值非法则报错并输出帮助后终止。
1. 确认当前工作目录存在 `src/`（工程根）；不存在则报告并终止。
2. 任务含 `cases` 时，检查 `test/cases/` 目录：
   - 存在且有用例文件 → 记录待执行清单。
   - 不存在或为空 → 提示用户"暂无场景用例"，跳过 cases 任务。
3. 若 `test/test-report.md` 已存在，先读取记录上一轮结果，供本轮报告中标注"回归对比"。

---

## 二、API 基本功能验证

仅当任务范围含 `api` 时执行：

1. 用 Skill 工具调用 **api-test** skill 执行全端 API 验证；将本命令收到的 `--no-fix`、用户提供的 `--base-url` 等参数透传给它。
2. /api-test 完成后确认产物存在：`test/api/url-list.md`、`test/api/test-result.md`。
3. 从 `test/api/test-result.md` 提取汇总数字（通过 / 修复 / 未解决 / 跳过条数）与未解决清单，供第四步引用。

## 三、场景用例验证

仅当任务范围含 `cases` 时执行。

**执行顺序**：`test/cases/case-summary.md` 存在时，按其中定义的优先级排序执行（P0 → P1 → P2，同优先级按用例编号升序）；摘要中未收录的用例排在最后（按编号升序）。不存在 `case-summary.md` 时按默认顺序执行（文件名/编号升序）。

### 3.1 用例格式

`test/cases/` 下每个 `.md` 或 `.yaml` 文件是一个测试场景（标准用例由 /new-test-case 生成，命名 `TEST-CASE-{4位编号}.md`）。`case-summary.md` 是摘要索引文件（由 /new-test-case 维护），**不作为用例执行**。Markdown 用例为专业模板结构：

- **元信息**：用例编号、测试类型（API / UI(Playwright) / 混合）、优先级、创建时间
- **前置条件**：执行前必须成立的状态
- **测试数据**：数据依赖及准备方式
- **测试步骤**：步骤表，每步含 类型 / 操作 / 输入参数 / 预期结果。类型三种：
  - `API`：接口请求（方法 + 路径 + 参数）
  - `UI`：Playwright 页面操作（goto/fill/click + 选择器 + 断言）
  - `人工`：需人工执行的操作（附操作指引）
- **结果验证**：全部步骤完成后的整体断言（数据状态、跨步骤一致性）
- **善后清理**：执行后的数据还原/清理操作

```markdown
## 测试步骤

| # | 类型 | 操作 | 输入/参数 | 预期结果 |
|---|------|------|-----------|----------|
| 1 | API | `GET /api/mall/products/1` | - | HTTP 200，且 price > 0 |
| 2 | UI | Playwright: goto `/login` → fill `#username` → click `button[type=submit]` | 测试账号 | 跳转至 `/home` |
```

兼容旧格式用例（"测试步骤"为编号列表 + "预期结果"列表），按原样执行。YAML 用例字段：`name`、`preconditions`、`steps`、`expected`。

结构不完整（缺步骤或预期结果）的用例标记 `无效用例`，跳过并在报告中列出。

### 3.2 执行规则

**执行方式（必做）**：每个用例单独委托一个子智能体（Agent 工具，subagent_type 用 general-purpose）执行，主循环只传入用例文件路径与相关上下文，接收其返回的用例结论；严格逐条串行，同一时刻最多只有一个子智能体在运行，上一个用例出结论后才启动下一个，禁止同时派出多个子智能体并行执行。

对每个用例（传入 `--case` 时只执行匹配项）：

1. **检查前置条件与测试数据**：能用 API/数据库查询验证的先验证；不满足时尝试构造（如先调登录接口、经用户同意造最小测试数据）；无法满足则标记 `阻塞` 并记录原因。
2. **逐步执行**，按步骤类型：
   - `API` → curl 实际请求（复用 /api-test 阶段的 base url 与 token）。
   - `UI` → 工程支持 Playwright（存在 playwright 依赖/配置）时，将 UI 步骤转写为临时 spec（`test/.tmp-case-<编号>.spec.ts`，headed=false）运行后删除；不支持时标记 `需人工` 并给出 Playwright 操作步骤指引。
   - `人工` → 标记 `需人工`，输出操作指引与判定标准。
3. **逐步判定**：对照步骤表中"预期结果"判定每步 通过/失败；失败时保留实际响应/截图说明（截断 50 行内）。
4. **结果验证**：全部步骤执行后，逐条核对"结果验证"整体断言（需要时补发查询请求/数据库查询取证）；任一断言不成立则该用例判 `失败`。
5. **善后清理**：执行用例中定义的清理步骤（同样逐步判定），清理失败在报告中单列提醒。
6. **用例结论**：全部步骤与结果验证通过 → `通过`；任一失败 → `失败`；存在阻塞 → `阻塞`；存在需人工步骤且其余全通过 → `部分通过（待人工）`。
7. 传入 `--no-fix` 时只判定不修复；否则对可明确定位的失败（如接口 404、断言字段名错误、选择器失效），按最小化原则修复后重跑该用例，最多一轮。

## 四、汇总报告

将总结果写入 `test/test-report.md`（只写实际执行的任务对应章节，未执行的任务注明"本轮未执行"）：

```markdown
# 测试报告

测试时间：<YYYY-MM-DD HH:mm>
执行范围：API 验证 + 场景用例 N 个

## 一、API 基本功能验证（/api-test）

- 清单：test/api/url-list.md（M 条）；明细：test/api/test-result.md
- 结果：通过 X / 修复 Y / 未解决 Z / 跳过 W
- 未解决项：<列表，含原因>

## 二、场景用例（test/cases/）

| # | 场景 | 文件 | 结论 | 说明 |
|---|------|------|------|------|
| 1 | 下单流程 | order-flow.md | 通过 | - |
| 2 | 退款流程 | refund.md | 失败 | 步骤 3 实际返回 500（已修复后复验通过 → 通过） |
| 3 | 后台审核 | admin-audit.md | 部分通过（待人工） | 步骤 2 需页面操作 |

结果：通过 a / 失败 b / 阻塞 c / 部分通过 d / 无效用例 e

## 三、结论与遗留问题

- 总体结论：<全部通过 / 存在未解决问题>
- 遗留问题清单：<未解决 API + 失败场景 + 需人工项>
- 修改文件清单：<本轮修复改动的文件>
```

同时向用户输出上述报告的中文摘要（总体结论 + 失败/阻塞项清单）。

## 五、注意事项

- /api-test 的交互确认规则（写操作逐条询问、凭据不落盘）在本 skill 中同样有效；透传用户已给出的确认，不重复询问。
- 探测使用的账号、token 只出现在请求中，不写入文件、不在报告中明文输出。
- 造测试数据、执行写操作前必须经用户确认，并说明作用于当前后端环境。
- 工程根目录 `v0/` 是只读产品设计文档，禁止修改。
- **必须串行执行**：本 skill 全程单实例、每个用例委托子 agent 逐条串行执行，禁止并行（多实例、多个子 agent 同时执行多用例、与 /aibug 或 /aicase 并发均不允许）；用户要求并行时应明确拒绝并说明该约束。
- 本 skill 只修改代码文件与 test/ 下的产物文件，不执行 `git commit`，由用户决定是否提交。
