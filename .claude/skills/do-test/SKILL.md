# do-test

驱动工程中所有测试场景的执行：API 基本功能验证（委托 /api-test）+ 场景用例验证（test/cases/），汇总为统一测试报告。

**定位**：测试编排入口。本身不做具体探测逻辑，API 部分完全委托 /api-test，场景部分按用例定义执行。

**触发条件**：用户要求运行全部测试、执行测试场景、回归验证，或直接输入 /do-test。

---

## 零、参数处理

**如果用户传入 `-h` 或 `--help`**，不执行任何操作，直接输出以下帮助信息后结束：

---

```
用法: /do-test [选项]

选项（通过命令行传入的参数直接使用，不再交互询问）
  --skip-api        跳过 API 基本功能验证（/api-test 部分）
  --skip-cases      跳过 test/cases/ 场景用例验证
  --case=<名称>     只执行指定场景用例（文件名或场景名，可多次传入）
  --no-fix          只检查并输出报告，不修改任何代码
  -h, --help        显示本帮助

工作流程
  1. 前置检查：确认工程结构（src/ 存在）、确认 test/cases/ 是否有用例
  2. API 验证：调用 /api-test skill，全端扫描 API 并逐个验证 HTTP 200、
     检查业务合理性，产出 test/api/url-list.md 与 test/api/test-result.md
  3. 场景验证：逐个读取 test/cases/ 下的用例文件，按步骤执行并判定结果
  4. 汇总报告：合并两部分结果写入 test/test-report.md，输出中文摘要

产物
  test/api/url-list.md     API URL 清单（由 /api-test 产出）
  test/api/test-result.md  API 验证与修复结果（由 /api-test 产出）
  test/test-report.md      总测试报告（API 结果 + 场景用例结果）

示例
  /do-test                     完整执行：API 验证 + 全部场景用例
  /do-test --skip-api          只跑场景用例
  /do-test --case=下单流程     只执行指定场景
  /do-test --no-fix            只出报告，不改代码
  /do-test -h                  显示本帮助
```

## 一、前置检查

1. 确认当前工作目录存在 `src/`（工程根）；不存在则报告并终止。
2. 检查 `test/cases/` 目录：
   - 存在且有用例文件 → 记录待执行清单。
   - 不存在或为空 → 提示用户"暂无场景用例，将只执行 API 验证"，继续。
3. 若 `test/test-report.md` 已存在，先读取记录上一轮结果，供本轮报告中标注"回归对比"。

---

## 二、API 基本功能验证

除非传入 `--skip-api`：

1. 用 Skill 工具调用 **api-test** skill 执行全端 API 验证；将本命令收到的 `--no-fix`、用户提供的 `--base-url` 等参数透传给它。
2. /api-test 完成后确认产物存在：`test/api/url-list.md`、`test/api/test-result.md`。
3. 从 `test/api/test-result.md` 提取汇总数字（通过 / 修复 / 未解决 / 跳过条数）与未解决清单，供第四步引用。

---

## 三、场景用例验证

除非传入 `--skip-cases`。

### 3.1 用例格式

`test/cases/` 下每个 `.md` 或 `.yaml` 文件是一个测试场景（标准用例由 /new-test-case 生成，命名 `TEST-CASE-{4位编号}.md`）。Markdown 用例约定结构：

```markdown
# 场景：下单流程

## 前置条件
- 已登录测试账号
- 商品 id=1 存在且库存 > 0

## 测试步骤
1. GET /api/mall/products/1，获取商品价格
2. POST /api/mall/orders 创建订单，body 含 productId=1
3. GET /api/mall/orders/{返回的订单id} 查询订单详情

## 预期结果
- 步骤 1 返回 200 且 price > 0
- 步骤 2 返回 200，响应含 orderId
- 步骤 3 返回 200，状态为待支付，金额与步骤 1 一致
```

YAML 用例字段：`name`、`preconditions`（列表）、`steps`（列表）、`expected`（列表，与 steps 一一对应）。

结构不完整（缺步骤或预期结果）的用例标记 `无效用例`，跳过并在报告中列出。

### 3.2 执行规则

对每个用例（传入 `--case` 时只执行匹配项）：

1. **检查前置条件**：能用 API/数据库查询验证的先验证；不满足时尝试构造（如先调登录接口、经用户同意造最小测试数据）；无法满足则标记 `阻塞` 并记录原因。
2. **逐步执行**：按步骤实际操作——API 调用用 curl（复用 /api-test 阶段的 base url 与 token），数据库断言用工程配置的查询方式，需要页面/UI 操作的步骤标记 `需人工` 并给出操作指引。
3. **逐步判定**：对照预期结果判定每步 通过/失败；失败时保留实际响应（截断 50 行内）。
4. **用例结论**：全部步骤通过 → `通过`；任一失败 → `失败`；存在阻塞 → `阻塞`；存在需人工步骤且其余全通过 → `部分通过（待人工）`。
5. 传入 `--no-fix` 时只判定不修复；否则对可明确定位的失败（如接口 404、断言字段名错误），按最小化原则修复后重跑该用例，最多一轮。

## 四、汇总报告

将总结果写入 `test/test-report.md`：

```markdown
# 测试报告

测试时间：<YYYY-MM-DD HH:mm>
执行范围：API 验证 + 场景用例 N 个

## 一、API 基本功能验证（/api-test）

- 清单：test/api/url-list.md（M 条）；明细：test/api/test-result.md
- 结果：通过 X / 修复 Y / 未解决 Z / 跳过 W
- 未解决项：<列表，含原因>

## 二、场景用例（test/cases/）

| # | 场景 | 文件 | 结论 | 说明 |
|---|------|------|------|------|
| 1 | 下单流程 | order-flow.md | 通过 | - |
| 2 | 退款流程 | refund.md | 失败 | 步骤 3 实际返回 500（已修复后复验通过 → 通过） |
| 3 | 后台审核 | admin-audit.md | 部分通过（待人工） | 步骤 2 需页面操作 |

结果：通过 a / 失败 b / 阻塞 c / 部分通过 d / 无效用例 e

## 三、结论与遗留问题

- 总体结论：<全部通过 / 存在未解决问题>
- 遗留问题清单：<未解决 API + 失败场景 + 需人工项>
- 修改文件清单：<本轮修复改动的文件>
```

同时向用户输出上述报告的中文摘要（总体结论 + 失败/阻塞项清单）。

## 五、注意事项

- /api-test 的交互确认规则（写操作逐条询问、凭据不落盘）在本 skill 中同样有效；透传用户已给出的确认，不重复询问。
- 探测使用的账号、token 只出现在请求中，不写入文件、不在报告中明文输出。
- 造测试数据、执行写操作前必须经用户确认，并说明作用于当前后端环境。
- 工程根目录 `v0/` 是只读产品设计文档，禁止修改。
- 本 skill 只修改代码文件与 test/ 下的产物文件，不执行 `git commit`，由用户决定是否提交。
