# git-summary

把一段提交区间里的 commit message **加工成功能清单**，而不是逐条罗列提交。默认区间 = 当前分支的**创建时间点**至今。

> **定位：只读汇总类任务。** 正文即功能清单，不输出 common-rules 规范一的四件套尾注，只压成一行起止时间（详见第四节）。全程只读，禁止任何改动仓库状态的操作。

## 零、参数处理

**如果用户传入 `-h` 或 `--help`**，不执行任何操作，直接输出以下帮助信息后结束：

```
用法: /git-summary [选项]

选项
  --branch=NAME       目标分支（可选，默认当前分支；支持本地名或 origin/xxx）
  --base=NAME         显式指定基线，区间 = 基线..分支（优先级最高）
  --since=DATE        区间起点，只接受时间值：YYYY-MM-DD / YYYY-MM-DDTHH:MM / 今天 / 昨天 / 前天
                      （按提交时间过滤；tag / 分支作起点一律用 --base）
  --limit=N           只取区间内最近 N 条提交参与加工（可选，正整数；默认不限）
  --raw               输出原始逐条提交列表与统计，不做归并加工
  --domain-map=PATH   自定义功能域词典文件（每行一个域名，覆盖内置词典）
  --with-merges       加工时包含 merge 提交（默认排除，merge 提交不携带功能信息）
  -h, --help          显示本帮助

默认区间口径（不加 --base/--since 时）：当前分支创建时间点 → 分支 tip。
区间起点只有三种来源：--base → --since → merge-base(默认基线, 分支)，**没有第四种**；
不做上探/下探（不沿版本族换基线、不自动改用 tag 或别的分支），区间窄也照实输出。
无独有提交或无功能增量时输出「区间性质判定 + 候选建议（须显式 --base 才生效）」，
不渲染空清单，也不会自动展开整条仓库历史。

输出形状：表头 → 新增/修复/口径与约定变更三段 →（可选）内部改造 → 未列入 → 一行极简总结 → 起止时间。

示例
  /git-summary                                  # 当前分支自创建点以来的功能清单
  /git-summary --base=feat-1.3.5                # 只列本版相对上一版的增量
  /git-summary --base=v1.4.7                    # 从 tag 起算（集合差口径）
  /git-summary --since=2026-09-01 --raw         # 原始列表，最近一个月
  /git-summary --limit=30                       # 只用最近 30 条提交加工
```

## 一、参数解析

| 命令行写法 | 对应参数 |
|---|---|
| `--branch=NAME` | `BRANCH`（默认 `git branch --show-current`） |
| `--base=NAME` | `BASE_REF`（可选，最高优先级） |
| `--since=DATE` | `SINCE`（可选，**只接受时间值**：`YYYY-MM-DD` / `YYYY-MM-DDTHH:MM` / `今天`/`昨天`/`前天`；tag / 分支作起点用 `--base`） |
| `--limit=N` | `LIMIT`（可选，正整数；**语义是"区间内最近 N 条提交"**，不是功能项条数） |
| `--raw` | 原始列表模式：跳过 3.1–3.4 的拆句/去噪/归并/定性，逐条输出提交原文与统计，作为功能清单的核对底稿 |
| `--domain-map=PATH` | 自定义功能域词典 |
| `--with-merges` | 包含 merge 提交 |

- 分支名支持位置参数：`/git-summary feat-1.3.6` 等价 `--branch=feat-1.3.6`。
- 时间一律东八区：取时命令前置 `TZ=Asia/Shanghai`；日期口径统一 author date（`%ad`），不与 committer date 混用。
- 分支 ref 解析：原样 `git rev-parse --verify --quiet "<name>^{commit}"`，失败再试 `refs/heads/<name>`、`refs/remotes/origin/<name>`；仍解析不到 → 报错并 `git branch -a --format='%(refname:short)' | head -15` 列出候选，不猜测。

## 二、区间解析（决定"从哪开始"）

按优先级取第一个可用者作为 `RANGE`：

1. **`--base=<ref>`**：`RANGE="<BASE_REF>..<BRANCH>"`，直接用，不再探测。
2. **`--since=<日期>`**：`RANGE="<BRANCH> --since=<日期>"`。**只接受日期**，传 tag / 分支直接报错并提示改用
   `--base`（那是 ref 集合差，两种口径不重复表达）。它与 `--base` 不是一回事，用之前要知道差别：
   - **合法取值只有时间形式**：`YYYY-MM-DD`、`YYYY-MM-DDTHH:MM`，或 `今天` / `昨天` / `前天`（先按东八区
     换算成 `YYYY-MM-DD`，命令固定 `TZ=Asia/Shanghai date`）。tag、分支名、以及 `2 weeks ago` 这类相对日期
     一律拒绝，报错提示"起点是 ref 请改用 `--base=<ref>`"，不猜测、不悄悄转换。
   - `--base=<ref>` 是**集合差**（`ref..branch`，只算分支独有提交）；`--since=<日期>` 是**时间窗口**，同期从
     基线同步/合并进来的提交也会被算进来，且历史遍历遇到早于该日期的提交就停止下探。
   - 实测（git 2.43）`--since` 过滤的是 **committer date**：author date `2026-06-24 20:08`、committer date
     `2026-06-25 14:54` 的提交，cutoff 拨到 06-25 12:00 仍在结果里，拨到 06-25 16:00 才消失。而本 skill 表头
     与逐条日期一律展示 author date（`%ad`），两者口径不同，rebase / cherry-pick 过的分支上，日期起点可能与
     表头时间对不齐——要精确框区间仍优先用 `--base`。
3. **分支创建点（默认，也是唯一的自动口径）**：先定默认基线 `BASE`（`origin/HEAD` → 本地/远端 `main` →
   `master`），再 `START=$(git merge-base "$BASE" "$BRANCH")`，`RANGE="$START..$BRANCH"`。
   分叉点只用来划区间，**不把它的时间当分支创建时间**（分支中途同步过基线，分叉点会前进）；区间的起始时间
   取区间内最早一条提交的 author date（`%ad`）。
4. **区间为 0 条时**（分支已并进基线、或分支即基线）：直接走第四节的「区间性质判定出口」，说明该分支相对
   基线无独有提交，结束。

**禁止替换基线（不做上探 / 下探）**：基线只能来自 `--base` / `--since` / 分支创建点三者之一。
不沿版本族往前换基线（`feat-1.4.7.5 → .4 → .3` 这类），不自动改用 tag 或别的分支当起点，
不因"区间只有几条提交"就改口径——区间窄就照实输出几条，判定与取舍交给读者；也不为"总得输出点东西"
展开整条仓库历史（历史上 300+ 条的大而全输出没有使用价值）。要更大或更小的口径由用户显式
`--base=<ref>` / `--since=<日期>` 指定。

取数命令（加工输入，`--raw` 用同一份数据）：

```bash
git log $MERGE_FLAG --reverse --date=format-local:'%Y-%m-%d' --pretty=format:'%h|%ad|%s' $RANGE
```

- `--limit=N` 时**先去噪（3.2）再截断**：从过滤后剩余的提交里按时间取最近 N 条，再正序加工（命令上是 `git log $MERGE_FLAG --reverse` 取全量后截断，不是 `git log -N` 先截断，否则小 `N` 容易被台账类提交占满、清单落空）。
- 取到列表后同时记录：区间起点短 hash 及其时间、区间提交数、时间跨度（首末条日期）、**基线来源**（见第四节表头取值），供表头与起止行使用。
- 空首行提交（`no message`）保留在计数里，加工时按 3.2 归入"未列入"。
- 正文按需读取（只对首行判不出对象、或需要核对具体结论的提交执行，属 commit message 范围，不算读 diff）：

```bash
git log -1 --date=format-local:'%Y-%m-%d' --format='%h %ad%n%B' <hash>
```

实测过本仓库存在大量"首行裸词、结论全在正文"的提交（如 48 条台账类里 19 条正文超 200 字符，写着闸门数量、唯一索引名、被跳过行回传旧票号这类实质结论），**只读首行会把它们全部屏蔽**，判读时按 3.1 的正文参与范围处理。

## 三、加工算法（五步，全部在本 skill 内由模型执行，不依赖脚本）

`拆 → 去噪 → 归并 → 定性 → 溯源`

### 3.1 拆：提交信息切子句

- 分隔符只认：`，`、`；`、`。`、` + `、`①②③④⑤⑥⑦⑧⑨`、换行。**顿号 `、` 与斜杠 `/` 不切**——前者是并列名词、后者常在同一个名词里（如 `订房/订餐双信封`），切开会把一件事拆坏。
- 一个子句 = 一个候选功能点；切出的子句不足 6 个字符或无名词主语的，并回前一句，不单独成项。
- 括号里的 scope（如 `feat(chat-style):`）只用于判断归属模块，不作为功能名。
- **默认按首行拆句**；首行是裸 `update`、台账留痕、或判不出对象时，**必须先读该提交正文再判定**（读命令见第二节），正文给出具体对象与结论的按正文入选，不得因首行信息不足直接丢进「未列入」。
- **正文参与范围只有三条**：① 救回首行无对象的提交；② 为已入选的功能项补原词（表名、索引名、闸门、错误码、票号等，仍受第五节约束 2 的"原样保留"）；③ 除此之外**不得**从正文派生出首行完全未涉及的新条目。经正文救回的条数在"未列入"一行注明"其中 x 条经正文补全入选"。

### 3.2 去噪：不入清单但计数

命中任一条即丢弃，并在末尾"未列入"一行按类别计数：

| 类别 | 判据 |
|---|---|
| 台账/留痕 | `台账`、`落账`、`留痕`、`补记`、`第 N 次`、`批…对齐` |
| 纯取证/跑测 | `test:` 前缀的提交（宣告通过/失败/负例/首轮，或描述判据调整），按下方封顶规则不入两段 |
| 裸词无对象 | `update`、`docs`、`chore`、`style` 等单字词，或"格式调整/临时调整/整理代码/小步调整/讨论后补充"这类判定不出对象的 |
| 空 message | `no message`、首行为空 |
| 无外部行为变化 | `refactor` / `chore` 且不改外部行为（表结构、接口、页面、口径、配置生效范围）；确有外部影响的进「内部改造」一行带过 |

**3.2 与 3.4 同时命中时，以 3.2 为准（提交级前缀封顶）**：一条提交首行的类型前缀决定它能进入哪一段，
子句内容不得反过来救回整条提交。

- `test:` / `docs:` / `chore:` 前缀的提交，其任何子句**一律不入**「新增」与「口径与约定变更」段——
  "改判三处判据""补负例断言"这类描述是**测试侧判据**，不是产品口径，把它抬成口径项就是把测试改动冒充成功能。
- 「口径与约定变更」只由 `feat:` / `fix:` 前缀、或无前缀但明确写出外部行为变化（表结构、接口、页面、
  计算口径、配置生效范围）的提交支撑。
- 确实只在 `test:` / `docs:` 提交里出现、看起来像产品口径的内容：计入对应「未列入」类别、不猜、不抬，
  由用户显式 `--base` / `--since` 换区间或指认提交后再纳入。
- 一条提交含多个子句时逐句判定，但封顶按整条提交的前缀生效（前缀是 `test:` 就整条不进两段）。

### 3.3 归并：按功能域聚类

- 归并键 = 子句里的名词主语（表名 / 模块 / 接口路径 / 页面 / 功能名）。同一功能域内"做了同一件事"的子句合成一行。
- 一条提交命中多个功能域时，**分别落到各自功能项下**（这是多数长提交的正常形态，不要为省事压成一项）。
- 内置功能域词典（`--domain-map=<文件>` 可整体覆盖，文件每行一个域名）：

```
库存与签收
申购与采购
退款与余额
核销与履约
订单与支付
会员与登录鉴权
四诊与报告
AI 问诊
商城与商品
门店端与BOSS
数据库与迁移
部署与配置
安全与合规
小程序与移动端
```

- 落不进任何域的子句归 `其它`，不得强行塞进现有域。

### 3.4 定性：每个功能项打一个标签

只有三段——**新增 / 修复 / 口径与约定变更**（含判定标准、计算口径、字段语义的调整）。refactor 类只在改变外部行为时入清单，且按实际影响归入上述三段之一。**先过 3.2 的「提交级前缀封顶」再定性**：前缀不允许的提交，子句再像口径变更也不入段。

### 3.5 溯源：每个功能项必须挂 hash

- 每个功能项末尾挂 ≥1 个 commit 短 hash，形如 `（046484a, 513297a）`。
- **挂不上 hash 的项不允许存在**；一个 hash 可支撑多项，一项也可由多个 hash 共同支撑。

## 四、输出契约

正文只有清单，不加寒暄、不加建议、不解释过程：

```
## 功能清单：<BRANCH>（区间 <START短hash>..<BRANCH短hash>，基线来源：<来源>，N 条提交 → M 个功能点）

### 新增
- **<功能名>**：<做了什么，一到两个分句，保留原文里的数字/错误码/接口路径>（<hash, hash>）

### 修复
- **<问题点>**：<修成什么样>（<hash>）

### 口径与约定变更
- <变更内容>（<hash>）

### 内部改造
<一句话，仅在存在时输出>（<hash>）

> 未列入：a 条台账/留痕、b 条裸 update/空 message、c 条纯取证提交。

总结：<一句话概览>

起止：<开始时间> ~ <结束时间>（东八区）
```

- **「总结」是固定槽位**，恒为一行（不超过 60 字），位于「未列入」之后、起止行之前，只允许由三部分拼成：
  区间规模（`N 条提交 → M 个功能点`）+ 条目数最高的 1–2 个功能域名 + 三段各自条数
  （`新增 x / 修复 y / 口径变更 z`）。写法如：`共 61 条提交 → 18 个功能点，集中在订单与支付、库存与签收（新增 7 / 修复 9 / 口径变更 2）`。
  所有数字必须与表头及三段实测计数完全一致（`新增 x / 修复 y / 口径变更 z` 是**清单实际渲染的功能项数**，
  不是 commit 前缀计数——多数提交没有 type 前缀，按前缀算必然错）；禁止出现清单里没有的功能名，禁止评价质量、禁止提建议或下一步。
  `M = 0` 时不输出该行（走区间性质判定出口，其定性行已承担总结职责，不重复）；`--raw` 模式不输出该行。
- **「基线来源」是表头固定槽位**，取值只能是 `用户指定（--base=<ref>）` / `用户指定（--since=<日期>）` /
  `分支创建点（merge-base）`。基线只能来自这三者，**没有第四种**；该字段写在括号内，
  禁止在括号外另挂一句解释（"不解释过程、形状必须一致"含此意）。
- 三段（新增 / 修复 / 口径与约定变更）固定渲染，某段无内容时该段写一行 `（无）`；`### 内部改造` 与 `> 未列入：` 两段**仅在确有内容时**输出。同一区间多次运行，输出形状必须一致。
- 功能项按重要度排序（影响资金/履约/权限的先列），不按 commit 顺序。
- 功能项超过 60 条时截断到 60 条并提示：`另有 x 个功能项未渲染，可用 --limit=N 收窄提交范围`。
- 最后一行起止时间即本 skill 对 common-rules 规范一的替代尾注：只读汇总任务，不输出影响范围/人工待办/飞书通知段。
- **`--raw` 模式**改为输出原始列表与统计：表头（分支、基线、分叉点、区间起始时间、提交数、时间跨度、作者数、类型分布）+ 逐条 `短 hash 日期 首行`（首行超 72 字符截为 71 + `…`）。**用途是核对底稿**——怀疑归并漏项、合并错功能域、或只想要逐条台账时用；它不去噪、不归并、不定性；提交数与功能点数没有固定大小关系（一条提交可拆出多项，一项也可由多条提交支撑），不要拿两者互相校验。分支即基线时区间为空，按第二节走区间性质判定出口，不展开整条历史、不换基线。

### 区间性质判定出口（空增量专用，替代三段模板）

命中任一条即输出下面这个形状，**不打三段清单、不打两个 `（无）`**——空表会被读成"清单坏了"，而事实往往是"这批提交本来就是台账 + 取证"：

- 区间为 0 条（分支已并进基线、或分支即基线）；或
- 入选项功能点 `M = 0`；或
- 区间内没有任何 `feat:` / `fix:` 前缀、也没有写出外部行为变化的提交（全是 `test:` / `docs:` / 台账类，按 3.2 封顶后必然为 0）。

```
## 区间性质：<BRANCH>（区间 <起短hash>..<止短hash>，基线来源：<来源>，N 条提交 → 0 个功能点）

本区间为 <一句话定性：迭代收尾台账 / 纯测试取证 / 相对基线无独有提交>，无产品功能增量。
提交构成：feat a 条 / fix b 条 / test c 条 / docs d 条 / 其它 e 条

如需更大口径（本 skill 不自动替换基线，须显式指定）：
  /git-summary --base=<候选分支或 tag>     # 候选（实测提交数）：<X（n 条）> / <Y（m 条）>

起止：<开始时间> ~ <结束时间>（东八区）
```

- 候选分支 / tag 与其提交数只是**给用户的建议**，必须来自本次实测（`git branch --format` + `git rev-list --count`），
  **不自动套用**；无可给候选时写 `候选：无`，禁止编造分支名或条数。
- 该出口只说明"这个区间没有功能增量、要看更大区间请显式指定"，**不展开整条历史、不另铺别的区间清单**。

## 五、硬约束（防止编造）

1. **信息源只有 commit message**（区间内取到的那批，含首行与按 3.1 正文参与范围读取的正文）。禁止读 diff、代码、文档去"补全"功能；禁止用外部知识命名一个提交里没有出现过的功能。
2. 功能项措辞只允许使用提交原文出现过的名词与结论；原文里的数字、错误码、接口路径、表名（如"未知分类判 400"、`chat_style_tag_bindings`）必须原样保留，不得泛化、不得四舍五入、不得改成"某接口""某表"。
3. 不得跨类型、跨渠道合并表述：原文按 `orderType` / 渠道 / 端 分句描述不同结论时，归并后必须各留各的，压成一句即判错。
4. 判定不了对象的一律进「未列入」，禁止猜一个功能名凑数；禁止为了三段齐全而把"内部改造"抬成"新增"，同样禁止把 `test:` / `docs:` 提交里的测试侧判据抬成"口径与约定变更"（见 3.2 封顶规则）。
5. 输出功能项数不得超过拆出的子句总数；每条必须可 hash 溯源；无增量时走第四节「区间性质判定出口」输出定性 + 候选建议（建议只作参考，不自动替换基线），不铺整条历史。
6. 统计数字（提交数、未列入计数、起止时间）必须来自本次实测命令输出，禁止估算或复用上一轮结果。

## 六、只读边界与回退

- 允许命令：`git rev-parse` / `rev-list` / `log` / `show` / `merge-base` / `describe` / `branch` / `shortlog` / `symbolic-ref`。禁止 `checkout`、`switch`、`fetch`、`pull`、`merge`、`rebase`、`reset`、`gc` 等任何改状态操作；需要补历史（浅克隆 `git rev-parse --is-shallow-repository` 为 true）时先征得用户同意。
- 不写文件，结果只输出到对话；用户显式要求导出时才写 `<分支名>-features.md` 到当前目录并告知路径。
- detached HEAD 且未指定 `--branch` → 用 `HEAD`，表头标注"游离 HEAD（非分支）"。
- 分支基于其它特性分支创建 → 区间会含父分支提交，末尾提示"如需只统计本分支增量，用 `--base=<父分支>` 重跑"。
- 浅克隆算不出分叉点 → 提示结果可能不完整，退化到 `git log $BRANCH --not $BASE` 并在表头注明"未找到共同祖先"。
- 本 skill 只做"读提交信息、归并成清单"，不判定代码质量、不做发布风险评估、不代替用户决定是否合并。
