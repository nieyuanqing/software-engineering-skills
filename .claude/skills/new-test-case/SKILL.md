# new-test-case

在 `test/cases/` 下新增**一个**测试场景用例文件。文件命名 `TEST-CASE-{4位递增编号}.md`，结构与 /do-test 的用例格式完全兼容，生成后可直接被 /do-test 执行。

**触发条件**：用户要求添加/新增测试用例、测试 case、测试场景。

---

## 零、参数处理

**如果用户传入 `-h` 或 `--help`**，不执行任何操作，直接输出以下帮助信息后结束：

---

```
用法: /new-test-case [场景描述]

一次执行生成一个用例文件：test/cases/TEST-CASE-{4位递增编号}.md
编号自动取现有 TEST-CASE-*.md 最大编号 + 1（无则从 0001 开始）。

工作流程
  1. 确定 test/cases/ 目录（不存在则创建）与下一个编号
  2. 收集场景信息：场景名、前置条件、测试步骤、预期结果
     （命令行已给描述则据此整理，缺项交互补齐）
  3. 写入 TEST-CASE-NNNN.md 并向用户展示内容摘要

示例
  /new-test-case 下单流程：登录后可用商品1创建订单并查询订单详情
  /new-test-case                 交互询问场景内容后生成
  /new-test-case -h              显示本帮助
```

---

## 一、确定编号

1. `test/cases/` 不存在则创建。
2. 列出已有 `TEST-CASE-*.md`，提取 4 位数字编号取最大值；新编号 = 最大值 + 1，不足 4 位前补零（无文件则 `0001`）。
3. 目标文件 `test/cases/TEST-CASE-<编号>.md` 已存在（异常情况）则顺延至下一个空编号。

## 二、收集场景信息

需要四项内容：**场景名、前置条件、测试步骤、预期结果**。

1. 命令行带了场景描述 → 据描述整理；可结合工程代码（后端 Controller、页面调用、test/api/url-list.md 若存在）推断具体 API 路径与参数，使步骤可执行。
2. 描述缺失或不足以成文 → **一次性**向用户询问缺项（场景名/步骤/预期）。
3. 步骤要求：每条是一个可执行动作（API 调用写明方法 + 路径 + 关键参数，或页面操作写明入口）；预期结果与步骤逐条对应、可判定（状态码、关键字段、取值关系）。

## 三、写入用例文件

按以下固定结构写入（占位符替换为实际内容）：

```markdown
# 场景：<场景名>

> 用例编号：TEST-CASE-<编号>
> 创建时间：<YYYY-MM-DD>

## 前置条件
- <条件 1，如：已登录测试账号>
- <条件 2，如：商品 id=1 存在且库存 > 0>

## 测试步骤
1. <动作 1，如：GET /api/mall/products/1，获取商品价格>
2. <动作 2，如：POST /api/mall/orders 创建订单，body 含 productId=1>

## 预期结果
- <步骤 1 的判定，如：返回 200 且 price > 0>
- <步骤 2 的判定，如：返回 200，响应含 orderId>
```

写入后向用户输出：文件路径、场景名、步骤数、预期数，并提示可用 `/do-test --case=<场景名>` 立即执行该用例。

---

## 四、注意事项

- 一次执行只生成一个文件；用户需要多个用例时逐个执行。
- 不修改已有用例文件；需要改旧用例时直接编辑对应文件，不经本 skill。
- 用例中不得写入真实账号密码等敏感信息，用"测试账号"等占位描述。
- 不执行 `git commit`，由用户决定是否提交。
